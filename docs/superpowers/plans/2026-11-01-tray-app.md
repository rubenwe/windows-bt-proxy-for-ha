# Tray App and Status Pipe Implementation Plan (plan 2 of 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A per-user tray icon (green / amber / red) with a status window and an elevated "show key", fed by a local named pipe that the service owns, plus a `status` command and tray autostart in `install`.

**Architecture:** The service gains a `StatusPipeServer` (`\\.\pipe\WindowsBtProxyForHA`): one newline-terminated JSON request and one response per connection, source-generated `System.Text.Json`. `status` is open to local interactive users; `key` needs a caller whose token is in Administrators, checked by the service at identification level. The same exe runs `tray`: a hidden Win32 window, a notify icon and a small status window, all plain P/Invoke. The tray polls the pipe and never needs admin; "Show key" relaunches `tray --show-key` through UAC. `install` registers the tray in `HKLM\…\Run` and starts it for the current user.

**Tech Stack:** .NET 11 Native AOT (as plan 1), `System.IO.Pipes` + `System.IO.Pipes.AccessControl` (`NamedPipeServerStreamAcl`), `LibraryImport` P/Invoke into user32/shell32/gdi32/kernel32, `Microsoft.Win32.Registry`, xUnit v3, pytest for the `status` interop check.

**Spec:** `docs/superpowers/specs/2026-11-01-windows-bt-proxy-for-ha-design.md` (§5.1 modes, §5.7 step 5, §5.8). Plan 1 (`docs/superpowers/plans/2026-11-01-core-proxy-service.md`) is done and released as 0.1.0.

**Not in this plan:** update status and the "Install update" button (plan 3, §5.9). The pipe protocol leaves room for an `update` request; nothing here sends one.

## Global Constraints

- Everything in plan 1's Global Constraints still holds: `net11.0-windows10.0.26100.0`, `SupportedOSPlatformVersion` `10.0.22000.0`, Native AOT, `TreatWarningsAsErrors`, `IsAotCompatible`, zero AOT/trim warnings, source-generated JSON only, one exe `windows-bt-proxy.exe`.
- P/Invoke only through `[LibraryImport]` (source-generated marshalling); no `[DllImport]` with non-blittable signatures. Window procedures are `[UnmanagedCallersOnly]` static methods.
- Pipe name `WindowsBtProxyForHA` (full path `\\.\pipe\WindowsBtProxyForHA`). Protocol version `1`. A request or response line is at most 4096 bytes of UTF-8 ending in `\n`. A server reads the request within 2 s or closes the connection. At most 4 pipe instances.
- Pipe ACL: deny NETWORK (`S-1-5-2`) all access; allow SYSTEM, BUILTIN\Administrators and the server process's own user full control; allow INTERACTIVE (`S-1-5-4`) read/write. Nothing else. The first instance is created with `PipeOptions.FirstPipeInstance`.
- `key` is answered only when the caller's token is in BUILTIN\Administrators (elevated). Every client that sends `key` connects with `TokenImpersonationLevel.Identification`. Every other client connects with `Identification` too: a pipe server is never given a token it could impersonate.
- Tray: never requires admin. Icon colours: green `#22A447` (any client subscribed), amber `#F2A900` (service reachable, no subscribed client, scanner not in a red state), red `#D93025` (service unreachable, scanner `NoAdapter`, `RadioOff` or `Failed`). Polling: status every 5 s for the icon, every 2 s while the status window is open. One tray per session: mutex `Local\WindowsBtProxyForHA.Tray`.
- Autostart: value `WindowsBtProxyForHA` under `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`. Its data comes from `Installer.TrayCommandLine(exe)`; Task 1 decides the exact form.
- Production HA (the author's): only add, reconfigure or remove this proxy's own ESPHome entries. The author runs elevated steps (install, uninstall, sc) and toggles the radio. Tests never run the host with mDNS on and never use the default pipe name. They pass `--pipe-name` / a unique name, because the installed service owns the default one on the author's machines.

## Review Focus

- **Explorer restarts (crash, update, `taskkill explorer`)** → the icon comes back by itself (`TaskbarCreated`). Pinned in Task 6 (`TrayControllerTests.Taskbar_recreated_re_adds_icon_with_current_light`).
- **Service hung, slow, or a pipe client that never writes** → the tray UI never blocks on the pipe, and the server drops the silent client after 2 s while it keeps answering others. Pinned in Task 3 (`StatusPipeServerTests.Silent_client_is_dropped_and_others_are_served`) and Task 6 (`TrayControllerTests.Only_one_request_in_flight`).
- **Upgrade or uninstall while trays run, possibly for several users** → `install` does not fail on the locked exe, trays move to the new version by themselves, and after `uninstall` trays exit and the folder goes. Pinned in Task 8 (`InstallerTests.Upgrade_moves_a_locked_exe_aside`, `InstallerTests.Uninstall_removes_run_value_before_the_folder`) and Task 5 (`TrayLifecycleTests`).
- **Pipe name already taken** (a squatter, or `run` while the service runs) → the proxy keeps running without a status pipe and logs a warning. A client never lends an impersonation-level token. Pinned in Task 3 (`Second_server_on_same_name_reports_in_use`, `Clients_connect_at_identification_level`) and Task 4 (`ProxyHostTests.Pipe_name_in_use_is_not_fatal`).
- **Non-admin asks for the key, or sends garbage / an oversized line** → `denied` / `bad-request`, the connection closes and the server is unaffected. Pinned in Task 3 (`Key_is_denied_to_non_admins`, `Oversized_request_is_rejected_without_allocating`).

### Task 1: Spike — no console window for `tray` (gate)

The exe is a console-subsystem program. Started from the Run key, from Explorer or through `runas`, it gets a console window, which is unacceptable for a tray icon. Windows 11 24H2 (build 26100) added the manifest setting `consoleAllocationPolicy` = `detached` and `AllocConsoleWithOptions`. With them a console app gets no console unless it asks for one. On older Windows 11 the setting is ignored. Hypothesis A, the default: the manifest says `detached`. Every verb except `tray`, `tray --show-key` and `service` calls `AllocConsoleWithOptions(ALLOC_CONSOLE_MODE_DEFAULT)` first thing: it attaches to the parent's console, or opens a window when there is none, as before. On Windows before 24H2, `tray` calls `FreeConsole()` when it is the only process on its console, so the window only flashes.

**Files:**
- Create: `spikes/ConsolePolicyProbe/` (tiny AOT console exe with the same manifest; logs to `%TEMP%\console-probe.log`: launch mode, `GetConsoleWindow() != 0`, `GetConsoleProcessList` count, before and after the attach call, whether stdout is a console/pipe/none)
- Create: `src/WindowsBtProxy/app.manifest`, `src/WindowsBtProxy/Hosting/ConsoleAttach.cs`
- Modify: `src/WindowsBtProxy/WindowsBtProxy.csproj` (`<ApplicationManifest>app.manifest</ApplicationManifest>`), `src/WindowsBtProxy/Program.cs` (first statement)
- Modify: `docs/decisions.md` (new section "Console window for the tray")

**Interfaces:**
- Produces: `static class ConsoleAttach { static bool NeedsConsole(string[] args); static void Ensure(); static void ReleaseIfAlone(); }`. `NeedsConsole` is false for `service`, `tray` (with or without `--show-key`) and true otherwise. `Ensure` calls `AllocConsoleWithOptions(DEFAULT)` and ignores `EntryPointNotFoundException`, because on pre-24H2 the console already exists. `ReleaseIfAlone` calls `FreeConsole` when `GetConsoleProcessList` returns 1.
- Produces: `Installer.TrayCommandLine(string exe) -> string` (stub here returning `"\"{exe}\" tray"`; Task 8 uses it; this task records which form is final)

  ```csharp
  public static class PipeProtocol
  {
      public const string DefaultPipeName = "WindowsBtProxyForHA";
      public const int Version = 1;
      public const int MaxLineBytes = 4096;
      public static readonly TimeSpan RequestTimeout = TimeSpan.FromSeconds(2);
      // Reads up to the first '\n'; null on EOF, PipeLineTooLongException past MaxLineBytes (never buffers more than that).
      public static Task<string?> ReadLineAsync(Stream stream, CancellationToken ct);
      public static Task WriteLineAsync(Stream stream, string json, CancellationToken ct);
  }
  public static class PipeRequestTypes { public const string Status = "status"; public const string Key = "key"; }
  public static class PipeErrors { public const string Denied = "denied"; public const string BadRequest = "bad-request";
                                   public const string UnknownRequest = "unknown-request"; public const string Version = "version"; }
  public sealed record PipeRequest(int V, string Type);
  public sealed record KeyReply(string? Key);                       // Key = base64, null = no key stored
  public sealed record PipeResponse(int V, ProxyStatus? Status = null, KeyReply? Key = null, string? Error = null);
  internal static class PipeAcl { public static PipeSecurity Create(); }
  internal static class ClientToken { public static bool IsAdministrator(NamedPipeServerStream pipe); }   // pipe.RunAsClient + WindowsIdentity.GetCurrent + IsInRole(Administrators)
  public sealed class StatusPipeServer(string pipeName, Func<ProxyStatus> status, Func<KeyReply> key, ILogger log,
                                       Func<NamedPipeServerStream, bool>? isAdministrator = null)   // default ClientToken.IsAdministrator
  {
      // Completes when ct is cancelled. Returns false at once (after logging a warning) if the name is already taken.
      public Task<bool> RunAsync(CancellationToken ct);
  }
  public static class StatusPipeClient
  {
      // null when nothing listens (or it does not answer) within `timeout`; always TokenImpersonationLevel.Identification.
      public static Task<PipeResponse?> RequestAsync(string pipeName, string type, TimeSpan timeout, CancellationToken ct);
  }
  ```
- Server loop: a `SemaphoreSlim(4)`. For each slot it creates an instance (`NamedPipeServerStreamAcl.Create`, `InOut`, max 4, `Byte`, `Asynchronous`, plus `FirstPipeInstance` on the very first) and awaits a connection. It then hands the instance to a handler and loops. A handler reads one line within `RequestTimeout`, answers, flushes, waits for the client to drain (`WaitForPipeDrain`), and disposes. Exceptions in a handler are logged at Debug and never stop the loop. `RunAsync` returns `true` after cancellation, once every handler has finished.
- Rules: an unparsable line or a missing `type` gives `bad-request`. `v != 1` gives `version`. An unknown type gives `unknown-request`. A `key` request from a non-admin gives `denied`. The response always carries `v: 1`.

  - Not running from the install: `Stay` (dev builds are never touched).
  - Run value absent: `Exit` (uninstalled, or `install --no-tray`).

  - `installedVersion != ownVersion`: `RestartInto`. The new tray's own version equals the installed one, so this cannot loop.

- Install changes:

  2. If the target exe exists and `File.Copy` hits a sharing violation, rename it to `windows-bt-proxy.exe.<yyyyMMddHHmmss>.old` and copy again. A running image can be renamed, and trays then move to the new version on their own.

- Uninstall changes: `runKey.Delete()` comes right after the service is removed and before the folder. Removing the folder retries for up to 10 s as now.
